# Prompts

Copy-pasteable prompts for the two sync directions, plus the standing rules that belong
in the repo's `CLAUDE.md`.

Four prompts, because the work happens in two different places:

| § | prompt | runs in | when |
|---|---|---|---|
| 1 | First sync — bootstrap into the repo | Claude Code | once |
| 2 | Sync down — apply the design system to the repo | Claude Code | design changed |
| 3 | Prepare pull-back — report what the repo changed | Claude Code | repo changed |
| 4 | Pull-back — absorb it, regenerate, repair the kits | the design file | repo changed |

Start with **§0** — the standing rules. Most mistakes are prevented there, not in the
prompt.

---

## 0. Repo standing rules — paste into `CLAUDE.md`

Without this, every prompt has to re-explain the file ownership and one of them
eventually won't.

```md
## Design system — `packages/design-system/`

This package is the design system, shared byte-for-byte with the design file. Read
`packages/design-system/SYNC.md` before changing anything in it.

**Never hand-edit these — they are generated:**
- `src/css/*.css` — EXCEPT `fonts.css` and `base.css`, which are hand-written
- `src/tokens.ts`
- `src/tailwind-preset.js`
- `docs/ds-components.jsx`
- `MANIFEST.json`

To change a token value, edit `tokens/tokens.json` and run:
`cd packages/design-system && node tools/build-tokens.mjs && node tools/manifest.mjs`

To change a component, edit `src/components/<group>/Name.jsx` and run:
`cd packages/design-system && node tools/build-docs.mjs && node tools/manifest.mjs`

**In app code (`apps/**`):**
- Never hardcode a colour, radius, font size or spacing value that a token exists for.
  Use `var(--token)` or the Tailwind preset. `tokens/tokens.json` is the full list.
- Import components from `@medaris/design-system` (or `/core`, `/data`, …), never by
  deep path into `src/components/`.
- Before writing a new component, check whether one exists. Read its `.prompt.md`.
- UI copy is Turkish with Ottoman-madrasah vocabulary (köşk, ders, müderris, talebe,
  müfredat, müzakere, icâzet). Keep diacritics. Never translate or modernise these.
- Arabic content: `--font-arabic` (Amiri), `dir="rtl"`, `--lh-arabic`.
- Green (`--green`) means "create", in Nizam only. Never a primary button in Tedris.
- Do not round the odd pixel values (7, 9, 11, 13.5) to a 4px grid — they are deliberate.

Full rules: `packages/design-system/DESIGN_RULES.md`.
```

## 1. First sync — bootstrap

Only needed once, because `MANIFEST.json` is generated by Node and is not committed from
the design file (the hashes must match what the repo recomputes, byte for byte).

```
Bootstrap the design system into this repo.

Source: <path to the unzipped design-system folder>
Target: packages/design-system/     (create it)

Do this:

1. Copy the source in wholesale.

2. Generate the artefacts — none of these are committed from the design side:
   cd packages/design-system
   node tools/build-tokens.mjs
   node tools/build-docs.mjs
   node tools/manifest.mjs
   Report the fingerprint it prints.

3. Wire it up:
   - add to tsconfig.base.json paths:
       "@medaris/design-system":   ["packages/design-system/src/index.ts"]
       "@medaris/design-system/*": ["packages/design-system/src/*"]
   - import "@medaris/design-system/css" once at each app's root
   - if the repo uses Tailwind, add the preset:
       presets: [require("@medaris/design-system/tailwind-preset")]
   Match this repo's existing conventions — if libraries live in libs/ rather than
   packages/, use that, and tell me the path you chose so the design side matches it.

4. Paste the standing rules from §0 of this file into CLAUDE.md.

5. Add to CI:
   node packages/design-system/tools/manifest.mjs --check

6. Verify: nx typecheck design-system

Then report: the fingerprint, the path you used, and anything in this repo that already
overlaps the package (an existing UI library, an existing token file, a conflicting
import alias). Do not merge them yourself — list them.
```

Step 6's overlap report matters: if the repo already has a button component or a token
file, the design side needs to align naming with it rather than ship a competing set.

From then on, use §2 and §3.

## 2. Sync down — design system → repo

Run in Claude Code, at the repo root, with the new package folder available (downloaded
from the design file, or already copied to a temp path).

```
Sync the design system into this repo.

Source: <path to the design system folder>
Target: packages/design-system/

Do this:

1. Replace the target directory wholesale — delete it and copy the source in. Do not
   merge file-by-file and do not try to preserve local changes; if the repo has edits
   that are not in the source, STOP and list them instead of overwriting.

2. Verify the copy is exact:
   cd packages/design-system && node tools/manifest.mjs --check
   This must print "in sync". If it reports drift, the copy is incomplete — fix it and
   re-run. Do not regenerate MANIFEST.json to make the check pass; that hides the
   problem it exists to find.

3. Check nothing downstream broke:
   - nx typecheck design-system
   - nx build tedris nizam   (or the repo's equivalent)
   If a component API changed, app code may fail to compile. Report each failure with
   the file and the old/new prop — do NOT fix app code in this step.

4. Report before committing:
   - the fingerprint from MANIFEST.json
   - which files changed, grouped as: tokens / components / docs / generated
   - any app-code breakage from step 3

5. Commit only after I confirm:
   chore(ds): sync design system <fingerprint>
```

**Why "STOP and list them":** the repo may legitimately be ahead — someone added a
variant last week. Overwriting silently is how that work disappears. See §3.

## 3. Prepare pull-back — repo → design system

Run in Claude Code when the repo has changed the package and the design file needs to
catch up. This prompt produces a **report**, not an edit.

```
The design system in this repo has changed since it was last synced from the design
file. Produce a pull-back report I can hand to the design agent.

Last synced fingerprint: <fingerprint>   (or: last synced commit <sha>)

Do this:

1. Find every change to packages/design-system/ since that point.
   git diff <sha>..HEAD -- packages/design-system/

2. Classify each changed file:
   - HAND-WRITTEN, must travel: tokens/tokens.json, src/components/**/*.{jsx,d.ts,
     prompt.md}, src/components/**/index.ts, src/css/fonts.css, src/css/base.css,
     the .md files, package.json, project.json, tsup.config.ts, tsconfig.json
   - GENERATED, must NOT travel (it will be rebuilt): src/css/*.css (others),
     src/tokens.ts, src/tailwind-preset.js, docs/ds-components.jsx, MANIFEST.json
   If a GENERATED file changed but its source did not, flag it — someone hand-edited
   an output and their change is about to be lost.

3. For every changed component, state whether its PUBLIC API changed:
   - props added / removed / renamed
   - a prop's accepted values changed (e.g. a variant removed from a union)
   - a new required prop
   - default value changed
   Read the .jsx and the .d.ts. This is the single most important part of the report:
   it decides whether the design file's reference screens need repairing.

4. For every changed token, give old value -> new value, and its CSS variable name.

5. Flag anything that looks like it bypassed the system rather than extending it:
   a hardcoded hex/px in the package, a new variant that duplicates an existing one,
   a token added outside tokens.json. Quote the line.

6. Output:
   - a file list with classification
   - an API-change table (component | change | breaking?)
   - a token table (name | var | old | new)
   - the flags from step 5
   - the head commit sha

Do not edit anything. Report only.
```

Hand that report plus the changed hand-written files to the design agent, and use §4.

## 4. Pull-back — absorb it in the design file

Run in the design file. This is the prompt that has actual judgment in it.

```
Pull back these design-system changes from the repo.

<paste the report from §3, and attach or point at the changed files>

Do this, in order:

1. Copy the HAND-WRITTEN changed files into packages/design-system/. Whole files, not
   patches. Skip everything classified GENERATED — those get rebuilt in step 2.
   If a file I am giving you also changed here since the last sync, STOP and tell me:
   this design file is not a git checkout, so copying would clobber one side. The merge
   has to happen in the repo.

2. Regenerate, in this order:
   node tools/build-tokens.mjs    (if tokens.json changed)
   node tools/build-docs.mjs      (if any component changed)
   node tools/manifest.mjs

3. Repair the reference surfaces — only if the API-change table is non-empty:
   - docs/kits/tedris/*.jsx and docs/kits/nizam/*.jsx
   - src/components/*/*.card.html
   Find every call site of each changed component and update it to the new API. If a
   prop was removed, remove the usage; if one became required, supply a real value that
   fits the screen's content, not a placeholder.
   If the API table is empty, change nothing here — the screens consume the components
   and already reflect the new behaviour.

4. Read the change against DESIGN_RULES.md and GUIDE.md. Tell me if anything violates
   them — a hardcoded value where a token exists, a variant that duplicates one, green
   used outside a Nizam create action, a new colour that is not in the palette, UI copy
   that dropped diacritics or modernised the madrasah vocabulary.
   Distinguish two cases and say which it is:
   - the app bypassed the system  -> propose the fix to push back up
   - the app needed something the system lacks -> propose adding it properly

5. Show me the affected reference screens so I can see the change rendered.

6. Report the new fingerprint.
```

## Notes on running these

**The fingerprint is the handle.** Record it in the sync commit message. Every prompt
above either consumes or produces one; without it you are comparing directories by eye.

**Step 3 of §3 is where the value is.** Everything else in that report is mechanical and
git could tell you. Whether a component's public API changed is the one question that
decides how much work the pull-back is — and it needs reading two files and thinking.

**"STOP and list" appears in both directions deliberately.** The failure this setup is
actually vulnerable to is not a bad edit; it is a silent overwrite of work the other side
did. Both prompts refuse rather than guess.

**Keep pull-backs frequent.** These prompts get longer and riskier the more has changed.
A pull-back after one PR is a five-minute mechanical task; after a month it is an
archaeology project.
