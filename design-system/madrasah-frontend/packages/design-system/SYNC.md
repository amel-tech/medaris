# Sync contract & team workflow

How the design system travels from the design project into the codebase, and how the
team works around it without the two drifting apart.

---

## 0. Who needs access to what

**Nobody on the team needs access to the design file.** Everything they read ships inside
this package and lands in the repo with it:

| they want | they open |
|---|---|
| the rules | `DESIGN_RULES.md` |
| product context, tone, iconography | `GUIDE.md` |
| what a token looks like | `docs/foundations/` |
| what a component does, when to use it | `src/components/**/*.prompt.md` + `docs/` |
| a real screen to start from | `docs/kits/tedris/`, `docs/kits/nizam/` |
| how to import it | `README.md` |
| how the process works | this file |
| the exact prompts to run | `PROMPTS.md` |

`docs/index.html` is the front door — open it from a checkout and everything is one click
away. No build step, no server; it is plain HTML against the package's own CSS.

Access to the design file is needed only by whoever **authors** the system, and only
because that is where the reference screens and specimen pages are regenerated. It is not
a permission boundary on changing tokens or components — see §1.

---

## 1. Direction of travel

The design system is **the same set of files on both sides**, and either side may change
it. `git` is the merge mechanism; the fingerprint is the assertion that both sides agree.

```
DESIGN FILE (authoring surface)          CODEBASE (main)
packages/design-system/     ◄──────►    packages/design-system/
  tokens/tokens.json                      apps/tedris/  apps/nizam/  ← import from it
  src/components/
  src/css/  src/tokens.ts               CI: node tools/manifest.mjs --check
  docs/
```

Because the package has no design-file-specific dependencies — plain `.jsx`, plain CSS
variables, a zero-dependency generator — moving it in **either** direction is a file copy,
not a port. Nobody reinterprets a design; a directory is copied and a hash is verified.

**Engineers may edit tokens and components in the repo.** Often they should — a missing
disabled state is faster to add where it is needed than to request and wait for. The
change comes back here on the next pull-back (§4) and the reference screens are
regenerated against it.

### The one real constraint

**The design file is not a git checkout.** Pulling a change back is a *copy*, not a merge —
so if both sides edited the same file since the last sync, the copy clobbers one of them.

The mitigation is not a permission rule, it is short-lived divergence:

> **Pull from `main` before authoring here, not after.** Sync down, make the change, hand
> it up. Then the design file is only ever a few minutes ahead of `main`, and there is
> nothing to conflict with.

If you skipped that and both sides moved, do the merge **in the repo** — that is where git
is — then pull the merged result back down here.

### What is genuinely read-only

Only the **generated** files, and on both sides equally:

- `src/css/*.css` (except `fonts.css`, `base.css`)
- `src/tokens.ts`
- `src/tailwind-preset.js`
- `docs/ds-components.jsx`
- `MANIFEST.json`

They are outputs. Editing one works locally and is silently reverted by the next
generator run — the most likely way this setup fails, and the reason `check-tokens`
exists.

## 2. The fingerprint

`MANIFEST.json` carries a sha256 per file plus a **rollup fingerprint** — a short hash
identifying the whole system at a point in time.

```json
{ "version": "0.1.0", "fingerprint": "<12-hex>", "fileCount": 138, "files": { … } }
```

It answers, without judgment:

- *Did I copy everything?* — recompute, compare.
- *Are the two sides in step?* — compare fingerprints.
- *Did a generated file get hand-edited?* — `--check` names it.

```bash
node tools/manifest.mjs           # design side: regenerate after any change
node tools/manifest.mjs --check   # either side: verify nothing drifted
```

> **The manifest is a build output and is not committed from the design file** — it is
> generated by Node, so the hashes match byte-for-byte what the repo recomputes. Run
> `node tools/manifest.mjs` once on the first sync; from then on it travels with the
> package.

Quote the fingerprint in handoffs and PR descriptions. "Design system `a1b2c3d4e5f6`" is
unambiguous; "the latest design tokens" is not.

## 3. Design → code

> Ready-made prompts for every step below: **`PROMPTS.md`**.

**1 · Change it here.** Token value, component, or rule. Then, always, in this order:

```bash
node tools/build-tokens.mjs   # regenerate CSS / tokens.ts / tailwind-preset
node tools/build-docs.mjs     # rebuild the docs component bundle
node tools/manifest.mjs       # restamp the fingerprint
```

Skipping the second step is the usual mistake: the reference screens keep rendering the
previous version and you chase a bug that is not there.

**2 · Copy it up** with Claude Code:

- Copy `packages/design-system/` over the repo's copy — whole directory, replace.
- Run `node tools/manifest.mjs --check` inside it. Green means the copy is exact.
- Commit with the fingerprint: `chore(ds): sync design system a1b2c3d4e5f6`.

**3 · Engineers consume it.** They import from the package. A React app needs no rebuild
step — the CSS variables and components are already final.

**4 · Reference screens follow automatically.** `docs/kits/tedris/` and `docs/kits/nizam/`
are built from the same components, so a token change shows up in them without anyone
editing a screen. That is their job: they are the regression surface. If a change looks
wrong there, it will look wrong in the product.

---

## 4. Code → design (pull-back)

An engineer changed a token or a component and it merged to `main`. Bringing it back is
deterministic — the edit **is** the package files — and it is agent work. Prompts for the
report and the absorption: **`PROMPTS.md` §3–§4**.

**1 · Copy the changed paths down** from `main` into `packages/design-system/` here.
Whole files, not patches.

**2 · Regenerate.** The derived artefacts are not merged, they are rebuilt:

```bash
node tools/build-tokens.mjs   # if tokens.json moved
node tools/build-docs.mjs     # if any component moved
node tools/manifest.mjs
```

**3 · Repair the reference screens — the only judgment step.** Two cases:

- **Token value, or a component changed behind a stable API.** Nothing to do. The screens
  consume the components, so they already show the new behaviour. Look at them; that is
  the review.
- **A component's API changed** — a prop renamed, a variant removed, a new required prop.
  Then `docs/kits/**` and the specimen cards call it the old way and must be updated.
  This is where an agent earns its keep: mechanical, but it needs reading the diff.

**4 · Check the change against the rules.** A repo-side edit can be correct code and still
be wrong for the system — a hardcoded hex, a fourth button variant that duplicates an
existing one, a 16px where a token exists. Read it against `DESIGN_RULES.md`. If it
violates them, fix it here and push the fix back up rather than absorbing the drift.

**5 · Confirm both sides agree:** `node tools/manifest.mjs --check`, then note the
fingerprint.

This is the loop that keeps the two honest. The design file is not a gate on the
codebase; it is where the system is kept coherent after the fact.

---

## 5. Who does what

| role | may edit | should not |
|---|---|---|
| **Design (here)** | anything hand-written: `tokens.json`, components, `.d.ts`, `.prompt.md`, rules, kits | let the design file sit ahead of `main` for days |
| **Engineers** | app code; **and** tokens/components in the repo when they need to | hardcode a value a token exists for; add a variant without reading the rules |
| **Sync (agent)** | copies, regenerates, repairs kits, checks against the rules | hand-edit a generated file; merge by copying over a diverged file |

## 6. When an engineer needs a change

Two routes, and **both are legitimate** — pick by how sure you are.

**Route A — just do it in the repo.** Right when the change is small and obvious: a
missing `disabled` state, a variant that clearly belongs, a token that is plainly absent.
Ship it, and it comes back here on the next pull-back (§4). Faster than asking, and the
system still catches up.

**Route B — ask first.** Right when the change is a *decision*: a new colour, a fifth
button variant, a different spacing rhythm, anything that sets precedent. Describe the
**need**, not the fix — "the course card needs a disabled state", not "add `opacity: .5`
to Card". Those questions are cheap to answer and expensive to get wrong in five places.

The failure mode is not editing the repo. It is editing the repo **and nobody pulling it
back**, so the two drift and the fingerprint stops meaning anything. Pull back often and
Route A is safe.

What is never right, either route: hand-editing a generated file, or solving a
system-level gap with a one-off local hack that nobody sees again.

## 7. Guardrails

In the codebase CI:

```bash
node packages/design-system/tools/manifest.mjs --check
```

This does **not** forbid editing the package — it forbids a *generated* file being out of
step with its source. An engineer who edits `tokens.json` and reruns the generator passes;
one who hand-edits `colors.css` fails, which is exactly the edit that would have been
silently lost.

Before any handoff from here:

```bash
node tools/build-tokens.mjs && node tools/build-docs.mjs && node tools/manifest.mjs --check
```

Catches the other likely failure: handing over a package whose generated files are stale
relative to `tokens.json`.

Optionally, a lint rule in the codebase banning hex colours and raw px in app code — not
in the package — so tokens do not quietly get bypassed.

## 8. Adding a component

Five files, or it is only half-exported:

1. `src/components/<group>/Name.jsx` — the implementation.
2. `src/components/<group>/Name.d.ts` — props, each documented, with `@default`.
3. `src/components/<group>/Name.prompt.md` — what it is, when to use it, one example.
4. `src/components/<group>/index.ts` — add the `export` and the `export type`.
5. `tsup.config.ts` — only if you added a whole new group.

Then: `node tools/build-docs.mjs`, add it to a specimen card, use it in a kit screen if it
belongs there, regenerate the manifest.

## 9. Adding a token

1. `tokens/tokens.json` — `$value`, `$type`, `$name` (the exact CSS variable name), and
   `$description` if the name is not self-evident.
2. Regenerate + restamp.
3. New top-level group? Add it to `GROUP_FILES` in `tools/build-tokens.mjs`, or it lands
   in `misc.css`.
4. Wanted in Tailwind? Add a `pick("<group>")` line to the preset section.

Compose from existing primitives — `--transition-hover` is built from `var(--dur-fast)`
and `var(--ease-standard)`, not literals — so changing a primitive changes everything
derived from it.

---

## 10. Review rhythm

- **Per change:** regenerate, sync, fingerprint in the commit message.
- **Pull back often.** This is the one habit the whole setup rests on. A repo-side change
  that sits unmerged for a week is how the two copies stop being one thing.
- **Weekly-ish:** skim `docs/kits/` — they are built from the real components, so drift
  between intent and implementation shows up there first.
- **When adding a product surface:** start from the closest kit screen rather than a blank
  file. It is already correct on spacing, type and vocabulary.

## 11. When design and code disagree

Neither side simply wins — but they are authoritative about different things.

The **codebase** is authoritative about what ships. If it works in production, that is a
fact, not an opinion.

The **design file** is authoritative about intent — `DESIGN_RULES.md`, `GUIDE.md`: why a
value is what it is, and what the system will and will not do.

So when they diverge, ask which kind of disagreement it is:

- **The app bypassed the system** — a hardcoded `#64748b`, a `16px` where a token exists.
  A bug in the app. Fix the app; do not update the docs to match it.
- **The app needed something the system lacks** — the drift is a signal, not a defect.
  Add it to the system properly, then remove the workaround.
- **The rule was wrong** — it happens. Real screens teach you things a token table cannot.
  Change the rule deliberately, in `DESIGN_RULES.md`, and say why. An undocumented
  exception becomes an undocumented second system.
