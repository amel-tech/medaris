# MDRS-110 — lesson duration in minutes, and session times in the viewer's zone

## What was done

**tedrisat**

- `lessons.duration_minutes` (integer, nullable) and `courses.time_zone`
  (text, `NOT NULL DEFAULT 'Europe/Istanbul'`) — migration
  `0019_lesson_duration_minutes_course_time_zone`, generated by drizzle-kit;
  the backfill `UPDATE` was appended by hand below the generated statements.
- Backfill rule: a `duration` that is a number with an optional minute unit
  (`dk`, `dk.`, `dakika`, `min`, `mins`, `minute`, `minutes`, any case, any
  surrounding spaces) becomes that number when it is 1–1440, the range the API
  accepts. Anything else stays `NULL` — `"10 soru"` on a quiz, `"1 saat"`,
  `"yaklaşık 60 dk"`, `"0 dk"`, `"2000 dk"`, the empty string. The issue says "parse the digits"; taking the digits of
  `"10 soru"` would have produced a 10-minute quiz, so non-minute text is left
  unset instead of guessed.
- The old `lessons.duration` column stays in the schema and the database,
  marked deprecated. Nothing reads it and `GET /courses/:id` no longer returns
  it, but every lesson write keeps it in step as `"N dk"` (or `NULL`), so a
  rollback past 0019 still shows current lengths. Rollback:
  `rollbacks/0019_…down.sql`.
- `PUT /courses/:id` is a full replace for the length too: a lesson sent
  without `durationMinutes` now has none (before, an undefined key was simply
  not `SET` and the old length survived).
- API: `durationMinutes` (integer 1–1440) replaces `duration` on every lesson
  DTO and response; `timeZone` (IANA, `@IsTimeZone`) is on create, PATCH and
  PUT of a course and on every course response. `null`, `""` or a fixed
  offset such as `"+03:00"` is a 400, not a 500 on the NOT NULL column; a PUT
  that omits it keeps the stored zone. Any spelling `Intl` accepts is stored in
  its canonical form (`"europe/berlin"` → `Europe/Berlin`, `"Turkey"` →
  `Europe/Istanbul`), by `CourseService` on every write path. The global pipe's `forbidNonWhitelisted` makes a request that
  still sends `duration` a 400.
- Spec and typed client regenerated (`pnpm run openapi:tedrisat`). The
  generator also rewrote the `info.version` header of every generated file
  (0.1.5 → 0.2.0); those header-only changes were reverted, as earlier tasks
  did, so the diff carries only the contract change. `MeApi` is now handed out
  by `createTedrisatAPIs` as `api.me`.

**tedris-web and nizam-web**

- `lib/i18n/request.ts` passes a `timeZone` to next-intl, read from the
  `medaris-tz` cookie (default `Europe/Istanbul`). `NextIntlClientProvider` is
  rendered from the server layout, so the client inherits the same zone and
  server and browser format identically.
- `TimeZoneSync` (in `ClientProviders`) calls the `syncViewerTimeZone` server
  action once per browser tab (a `sessionStorage` flag): `users.time_zone`
  from `GET /me` when signed in and set, otherwise the browser's zone. Setting
  the cookie inside the action makes Next re-render the current route in the
  action's response (`pathWasRevalidated` in Next 16's `request-cookies.js`),
  so there is no separate `router.refresh()`.
- `SessionTime` shows a session in the course's zone and, when the viewer's
  clock differs, in theirs: "21:00 İstanbul · 20:00 senin saatinle". Used on
  the tedris syllabus rows, the lesson page header and the nizam curriculum
  list. The lesson page's curriculum rail (date only) and the live badge stay
  in the viewer's zone.
- nizam course form (C5): a "Saat dilimi" select (every zone
  `Intl.supportedValuesOf` knows). The live-lesson editor's date/time input is
  read and written in the course's zone, not the browser's, and its label
  names the zone. Changing the zone keeps every scheduled session at the same
  instant and re-expresses the typed times in the new zone. Duration is sent
  as `durationMinutes`; the editor will not save a length outside 1–1440.
- Zone helpers live in `@medaris/utils` (`libs/utils/src/time-zone.ts`), plain
  `Intl`, no new dependency.

B5, B7 and C5 are not in the design-system mirror (`design-system/`, read
through the `medaris-design-system` skill; MDRS-127 is designing them), so the
UI follows the existing patterns of each screen.

  No such copy is reachable from here. Before deploying, on a copy:

  ```sql
  -- after 0019: every text that did not become a number
  SELECT duration, count(*) FROM lessons
  WHERE duration IS NOT NULL AND duration_minutes IS NULL
  GROUP BY duration ORDER BY count(*) DESC;
  ```

  Each row is a text left unset on purpose or a pattern the rule missed.

## Follow-up

- Drop `lessons.duration` in a later migration, once this release is live
  everywhere.
- Deploy tedrisat together with tedris-web and nizam-web: an old nizam still
  sends `duration`, which the new API refuses with 400.
- A test runner for `libs/utils` would let the zone helpers be pinned in CI.
- `users.time_zone` has no UI yet; only `PATCH /me` sets it. A tab that was
  open before the user signed in keeps the browser zone until a new tab.
- `SessionTime`, `TimeZoneSync` and `syncViewerTimeZone` are copied into
  tedris-web and nizam-web (only the translation namespace differs), and the
  `SessionTime.*` keys into both locale files. No web lib today carries
  `next-intl`; moving them into one is a separate change.
- `cookies()` in `getRequestConfig` makes every route that uses next-intl
  request-dynamic. In tedris every page already was (the header reads the
  session); in nizam the `[locale]` welcome page and `/home` could have been
  static and no longer are. If that matters, the zone can instead be passed
  per call site from a cookie read only where sessions are shown.
