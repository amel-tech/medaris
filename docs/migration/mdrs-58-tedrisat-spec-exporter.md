# MDRS-58 — regenerate the tedrisat OpenAPI spec, and make it reproducible

Base: `origin/main` `cb7e9636`.

## What was wrong

MDRS-58 asked for the spec and the generated client to be refreshed, because
MDRS-27 had changed the wire contract of ten routes. The first thing measured
was *why* nobody had refreshed them, and the answer turned out to be the more
important half of the task.

**No script in the repository wrote `libs/services/swagger-docs/tedrisat.json`.**
Every reference to that path was a reader:

```
$ grep -rn "tedrisat.json" --include=*.ts --include=*.json --include=*.mjs \
      --include=*.js --include=*.yml --include=*.yaml --include=*.md . \
      --exclude-dir=node_modules
libs/services/package.json:22   dev:tedrisat       -> onchange 'swagger-docs/tedrisat.json' ...
libs/services/package.json:24   generate:tedrisat  -> openapi-generator-cli generate -i swagger-docs/tedrisat.json ...
libs/services/README.md, libs/services/swagger-docs/README.md, docs/*, tools/ai-review/lenses.yaml   (prose)
```

The file's only producer was `SwaggerModule.createDocument` at
`apps/tedrisat/src/main.ts:66`, inside a running service. Refreshing the
contract therefore meant booting tedrisat, opening Swagger UI and saving the
JSON by hand — and the drift that followed was worse than the issue described.
The issue expected a missing security requirement on ten routes; the committed
spec had never heard of those ten routes at all:

| | committed at `cb7e9636` | regenerated |
|---|---|---|
| `info.version` | `0.1.4` | `0.1.5` |
| paths / operations | 29 / 47 | 39 / 57 |
| `components.schemas` | 42 | 54 |
| `/flashcard-label/*`, `/flashcard-deck-label/*` | absent | 10 operations |

So the spec predated both `FlashcardLabelModule` controllers, not just
MDRS-27's guard.

## What changed

- **`apps/tedrisat/src/openapi/export-openapi.ts`** (new) — writes
  `libs/services/swagger-docs/tedrisat.json` from the live Nest metadata. This
  is the step that was missing.
- **`apps/tedrisat/src/config/openapi-document.ts`** (new) — the
  `DocumentBuilder` metadata, lifted out of `main.ts` so the exporter and the
  served document cannot describe different APIs.
- **`apps/tedrisat/src/main.ts`** — calls that factory instead of building the
  document inline. No behavioural change: `components.securitySchemes` is
  byte-identical before and after (verified below).
- **`apps/tedrisat/package.json`** — `openapi:export` script.
- **`apps/tedrisat/test/unit/openapi-document.spec.ts`** (new, 3 tests) — locks
  the `addBearerAuth()` / `addOAuth2(..., "bearer")` ordering. Reversing those
  two leaves an `{ type: "http", scheme: "bearer" }` scheme that still validates
  and no longer tells a client how to authenticate.
- **`apps/tedrisat/vitest.config.ts`** — excludes the exporter from coverage, on
  the same grounds as the existing `src/main.ts` and `src/otel.ts` entries.
- **`libs/services/swagger-docs/tedrisat.json`** — regenerated.
- **`libs/services/src/tedrisat/generated/**`** — regenerated by
  `pnpm --filter @medaris/services run generate:tedrisat`.
- **`libs/services/swagger-docs/README.md`** — documents the two-command
  refresh, in order.

Neither generated artifact was touched by hand.

## Which bootstrap, and why

The document needs an initialised application, and `AppModule` pulls in
`DatabaseService`, whose `onModuleInit` opens a `pg` pool and runs the migrator.
Two ways to get past that were considered:

**(a) `NestFactory.create(AppModule, { preview: true })` — chosen.** Preview
mode registers every module, controller and route in the container without
instantiating providers or firing lifecycle hooks, so the router metadata the
Swagger scanner reads is complete while nothing opens a socket. Measured: 39
paths emitted with no database running and no Docker daemon involved.

**(b) A live Postgres via `docker compose up`** — rejected. It would make
regenerating the contract depend on a running database, which is the friction
that let the spec go stale in the first place, and it would need Docker in CI.
It was not needed, so the `.env` / `docker/init-db.sql` password mismatch that
PR #53 (MDRS-68) addresses never came up here.

### (a) and (b) were proven to agree

Preview mode skipping provider instantiation is only safe if it changes nothing
the scanner reads. That was measured rather than assumed, using the existing
Testcontainers helper (`test/helpers/test-app.helper.ts`) to boot a **fully
initialised** app against a real `postgres:17-alpine` — migrations applied,
`Database connected successfully` — and building the document from the same
factory:

```
BOOTED_PATHS    39
BOOTED_MD5      bbc71802e971ea0a6d87d4167c4e92eb
COMMITTED_MD5   bbc71802e971ea0a6d87d4167c4e92eb
IDENTICAL       true
```

Byte-for-byte identical to the committed artifact. The probe was a throwaway and
is not part of this change.

### A finding that came out of that comparison

The first version of the probe ran under Vitest, and produced a document that
differed from the committed one in exactly 36 lines: six occurrences of
`"enum": ["PUBLIC", "PERSONAL"]` on the `scope` property of the label DTOs,
present in the Vitest document and absent from the committed one.

That is **not** a preview-mode artifact — re-running the same fully-booted probe
under `ts-node` produced the byte-identical result quoted above. It is a
transform difference. `create-flashcard-label.dto.ts:22` declares
`@ApiProperty()` with no `enum:` option and relies on `design:type` metadata for
`scope!: Scope`; `tsc` with `emitDecoratorMetadata` emits `String` there, while
the SWC transform `vitest.config.ts` installs (`decoratorMetadata: true`) emits
the `Scope` enum object, which `@nestjs/swagger` then expands.

`nest-cli.json` declares no SWC builder, so `nest build` uses `tsc` and the
**deployed** service serves `"type": "string"` with no enum — which is what the
committed spec now says. The spec is therefore faithful to production, and the
gap is that the DTO does not declare the enum it validates with `@IsEnum(Scope)`.
See the follow-up below.

## Reproducibility

Two things would otherwise make the artifact depend on who ran the script:
`config/security-env.ts` refuses to build a config without
`KEYCLOAK_JWKS_URL`, `KEYCLOAK_ISSUER`, `KEYCLOAK_AUDIENCE` and `DB_PASSWORD`,
and the first of those decides the two OAuth2 URLs in
`components.securitySchemes.bearer`. The exporter therefore reads those four
from the committed `.env.example`, through `tools/env/root-env.cjs` so the
`API__`/`TEDRISAT__` prefix rules stay in one implementation, and writes them
over whatever the ambient environment holds. It deliberately does not import
`./load-env` (which would apply the developer's own `.env`) or `./otel`.

Measured — four runs, one md5:

| run | conditions | md5 |
|---|---|---|
| 1 | clean shell, no root `.env` | `bbc71802e971ea0a6d87d4167c4e92eb` |
| 2 | immediately again (idempotence) | `bbc71802e971ea0a6d87d4167c4e92eb` |
| 3 | hostile env: `KEYCLOAK_JWKS_URL=https://hostile.invalid/...`, `KEYCLOAK_ISSUER`, `KEYCLOAK_AUDIENCE`, `DB_PASSWORD` all overridden, plus `NODE_ENV=production` and `SWAGGER_ENABLED=true` | `bbc71802e971ea0a6d87d4167c4e92eb` |
| 4 | with a root `.env` present (`cp .env.example .env`) | `bbc71802e971ea0a6d87d4167c4e92eb` |

Run 2 produced no diff at all — the second run is a no-op. No date, hash or
iteration-order noise was observed in the output.

One intentional byte-level change: the file now ends with a newline. The
hand-saved version did not.

## What the diff shows

Compared operation-by-operation against `HEAD:libs/services/swagger-docs/tedrisat.json`.

**Ten operations added, every one of them carrying the security requirement**
— `security: [{"bearer": []}]`:

```
POST   /flashcard-label/create              POST   /flashcard-deck-label/create
POST   /flashcard-label/labeling            POST   /flashcard-deck-label/labeling
GET    /flashcard-label/{id}                GET    /flashcard-deck-label/{id}
GET    /flashcard-label/getStats/{id}       GET    /flashcard-deck-label/getStats/{id}
DELETE /flashcard-label/delete/{id}         DELETE /flashcard-deck-label/delete/{id}
```

**403 and 404 on both delete routes**, with the descriptions from the
controllers:

```
/flashcard-label/delete/{id}       200, 403 "The label belongs to another user", 404 "No label with that id"
/flashcard-deck-label/delete/{id}  200, 403 "The label belongs to another user", 404 "No label with that id"
```

**The two removed request fields.** The issue expected `createdBy` and `userId`
to disappear from the request DTOs. On this base they cannot appear as removals,
because the label DTOs were never in the spec at all — the observable form is
that the four newly published request schemas do not carry them:

```
CreateFlashcardLabelDto           title, scope
CreateFlashcardLabelingDto        labelId, privateToUserId, flashcardId
CreateFlashcardDeckLabelDto       title, scope
CreateFlashcardDeckLabelingDto    labelId, privateToUserId, deckId
```

No `createdBy`, no `userId`, in any of the four.

**No operation was removed** and **no schema was removed** — `0` of each. The
security requirement on the 47 pre-existing operations is unchanged.
`components.securitySchemes`, `tags` and `servers` are all identical to the
committed values.

### Generated client

`.openapi-generator/VERSION` is unchanged at `7.14.0`, and
`.openapi-generator/FILES` lost no entry — nothing was orphaned. 14 files added,
53 modified, 0 deleted.

Of the 53 modifications, **40 are the version banner alone**
(`The version of the OpenAPI document: 0.1.4` → `0.1.5`) — expected churn on
every version bump, not a signal. The remaining 13 carry a real change, and each
one maps to a row in the drift table above or is generator bookkeeping:

```
FILES (14), models/index.ts (12), apis/index.ts (2)   the new label files

  CreateCourseDto, EnrolledCourseResponse               requiresApproval docs
```

None of the six `apis/*.ts` files that already existed changed beyond the

`FlashcardlabelApi.ts` and `FlashcardDeckLabelApi.ts` each call

`CreateFlashcardLabelDto.ts` declares `title` and `scope` only.

## Follow-ups

Recorded here rather than opened as issues.

1. **The spec was generated from `cb7e9636`, and PR #50 (MDRS-32) is still
   open.** That PR removes tedrisat's `example` module and the `MedarisResponse`
   envelope, and deletes `ExamplesApi.ts`, `CreateExampleDto` and the
   `MedarisResponse*` models from the generated client. Generating from `main`
   necessarily keeps them, because `main` still has the module — so the two
   diffs overlap heavily on both artifacts. **After #50 merges, re-run the two
   commands** (`openapi:export`, then `generate:tedrisat`); do not resolve it by
   editing either artifact.
2. **`Scope` should be declared on the DTO, not inferred.**
   `create-flashcard-label.dto.ts:22` and its deck counterpart validate with
   `@IsEnum(Scope)` but publish `@ApiProperty()`, so the contract says
   `"type": "string"` and never names `PUBLIC` or `PERSONAL`. Adding
   `@ApiProperty({ enum: Scope })` would state the two legal values and would
   also make the `tsc` and SWC transforms agree (see above). Left out here
   because it changes the contract's content rather than regenerating it, which
   is outside this issue's acceptance criteria.
3. **Nothing enforces that the spec stays current.** The exporter makes the
   refresh a command; it does not make a stale artifact fail a build. A CI step
   that re-runs the exporter and fails on a non-empty `git diff` would close
   this class of drift permanently. Not added here: it touches the workflow
   files that several open PRs are already editing.
4. **`GET /secure` has MDRS-58's own bug.** `app.controller.ts:72` carries
   `@UseGuards(AuthGuard)` but no `@ApiBearerAuth()`, so the spec publishes it
   with no `security` requirement and `TedrisatServiceApi.getSecureHello` sends
   no token — a client generated from the contract cannot call it successfully.
   Pre-existing and byte-identical in the old spec, so the regeneration only
   re-publishes the gap rather than introducing it. It is the same
   guard-without-`@ApiBearerAuth()` shape MDRS-27 fixed on the label
   controllers, and worth sweeping for across all controllers.
5. **`privateToUserId` is published as required but is optional in code.** Both
   labeling DTOs declare it `@IsOptional()` with a `null` default and annotate
   it with a bare `@ApiProperty()`, so the spec lists it in `required`. A client
   following the contract will always send it. Same class as follow-up 2 — the
   annotation does not state what the validator enforces.
6. **`libs/services` has a `generate` script that calls `pnpm run lint:fix`,
   which that package does not define.** Pre-existing; `generate:tedrisat` was
   used directly and is unaffected.
